# APS-500 / Wakespeed WS500

The Renogy APS-500 is a Wakespeed WS500 alternator regulator loaded with a Renogy configuration. It
reads the BMS over RV-C (the BMS's CAN1) and follows the charge voltage and current limits the BMS
publishes. This page covers its serial interface, how it polls the BMS, how it enforces a current
limit, the charge-collapse cycle the stock BMS causes, its fault codes and how to recover it. The
facts about the regulator come from disassembly of WS500 firmware 2.6.0 (an STM32F0 Cortex-M0 image)
and from CAN and serial captures of a running system.

## Identity on the bus

| Item | Value |
|---|---|
| Regulator source address | `0x80` (CAN ID setting = 128); every APS-500 frame ends in `…80` |
| BMS source address | `0x70` (`RBM ID` = 112) |
| BMS mode | `IsRBM` = 2, "Virtual RBM": the regulator re-broadcasts the BMS's data as standard RV-C |
| Bus | 250 kbit/s, 29-bit IDs |
| Expected model string | `P51S-12RBT210LF` (read from register `1402` at startup) |
| Alternator state while following the BMS | `AltState` 39, "CVCC mode, only available in system under direction of CAN master" |

## Serial interface

The regulator has a USB virtual COM port (CDC ACM, 115200 baud). It streams an `AST;` status line
about once a second. Commands are `$XXX:` strings, answered with `AOK;` plus whatever status strings
apply.

[`tools/ws500_serial.py`](../tools/ws500_serial.py) talks to it (needs pyserial). It refuses any
configuration-changing command unless `--allow-write` is given.

```sh
python tools/ws500_serial.py --port COM5                  # watch AST; lines for 6 s
python tools/ws500_serial.py --port COM5 '$RAS:' '$RLF:'  # all status strings, last fault
python tools/ws500_serial.py --seconds 20 --ast-only      # Linux finds the port itself
```

On a Unix shell, quote `$RAS:` in single quotes or the shell eats the `$`.

| Command | Effect |
|---|---|
| `$RAS:` | request all status strings (`CPE;` `CST;` `ENG;` `NPC;` `SCV;` `SST;`) |
| `$RCP:0` | request the selected charge profile |
| `$RLF:` | request the last fault, answered `FLT;,<code>,<required sensor status>` |
| `$SC…`, `$CP…`, `$CNG`, `$MSR`, `$RBT`, `$DEP`, `$CCN`, `$CDD` | write configuration or reboot the regulator |

One `AST;` line carries battery volts, amps, target volts and amps, field drive, state and
temperatures sampled together, so it is easier to correlate than CAN frames arriving at different
rates.

### Reading config and status strings

| Convention | Detail |
|---|---|
| Profile voltages are normalized to 12 V | Charge-profile voltages are for a nominal 12 V battery and multiplied at runtime by the system-voltage factor. The Renogy configuration forces that factor to 4.00 (`SCV;` field 4, the SV override), so a stored `13.20` means 52.8 V. Profile currents are likewise relative to a nominal 500 Ah battery and scaled by the capacity multiplier. |
| `AST;` uses real volts | `BatVolts`, `AltVolts` and `TargetVolts` in `AST;` are real system volts. |
| New fields are appended | Newer regulator firmware adds parameters at the end of a string. Decoding from the left is reliable; extra trailing fields are newer additions, and a config with fewer values lets the newest trailing ones default. |
| The Renogy profile is undocumented | The Renogy configuration is a limited-release profile that Wakespeed's public communications guide does not describe. Treat the guide's field lists as an approximate map; prefer live readback. |

Values in the Renogy configuration that matter here:

| Field | Value | Meaning |
|---|---|---|
| `acptVBAT`, `floatVBAT` (`CPE;`) | 13.20 | 52.8 V; the regulator's own profile target, overridden by the BMS limit |
| `TargetVolts` (`AST;`) | 54.70 | the BMS charge voltage limit, register `138F` word 0 |
| `MaxBatVolts` | 0.00 | the optional over-voltage fault is disabled |
| `VBat Comp` | 0.000 | no temperature compensation of the target |
| `$SCA` 0.31 / 0.23 | | current derate factors (31 % and 23 % of alternator capacity), not voltage offsets |
| CAN protocol (`CST;`) | 201 | Renogy BMS with Zero Output Technology; 200 is the same protocol with ZOT disabled |

With no remote battery sensor, `BatVolts` equals `AltVolts`: the regulator uses its alternator-side
measurement as the battery voltage, which includes the cable's IR drop.

## The poll cycle

The regulator reads BMS registers with RV-C proprietary requests: ID `0x18EF7080` (DGN `EF00`
addressed to `0x70`, priority 6), data `RR RR NN NN FF FF FF FF` (start register, count, both
big-endian). The BMS answers on `0x18EF8070`. See [can-protocol.md](can-protocol.md) for the BMS side.

| Order | Request | Content |
|---|---|---|
| startup | `1402`, 8 registers | model string |
| startup | `13A5`, 4 registers | |
| 1 | `1388`, 4 | pack data |
| 2 | `138F`, 4 | word 0 charge voltage limit (0.1 V), word 1 charge current limit (signed 0.01 A), then `1391`, `1392` |
| 3 | `1395`, 4 | temperatures (the regulator averages four) |
| 4 | `1388`, 4 | pack data again |
| 5 | `1392`, 4 | alarm registers `1392`–`1394` and status |
| 6 | `138A`, 4 | remaining / full capacity |
| 7 | `0043432A007D7900` | not a request (see below); never answered |

The cycle repeats about every 500 ms: each register is read twice a second and `1388` four times.
This needs the BMS to answer every poll; stock V137.4.5 drops many of them, which the CAN1
busy-release fix in every published recipe corrects ([can-protocol.md](can-protocol.md)).

**The stray frame is a WS500 off-by-one.** After the `138A` reply the regulator sends entry 8 of a
7-entry request table: a padding byte and the start of its own text-command table (`"CC*\0"` and a
code pointer). The BMS rejects it in its register range check, so the regulator waits about 230 ms
and restarts the cycle. Do not make the BMS answer register `0x0043`: a reply advances the
regulator's counter and it sends the next entry further into its command table.

### Charge limits the regulator applies

RV-C current is `raw = amps × 20 + 32000` (0.05 A/bit). The regulator clamps the raw value to
33800 with a literal in its `138F` handler, so **the largest charge current it ever targets is
90 A**, whatever the BMS publishes. Stock V137.4.5 publishes 105 A.

| BMS `138F` word 1 | raw | after the clamp | `TargetAmps` |
|---|---|---|---|
| −105.00 A (`D6FC`) | 34100 | 33800 | 90.00 A |
| −42.00 A (`EF98`) | 32840 | 32840 | 42.00 A |

Word 0 `0x0223` (547 × 0.1 V) gives `TargetVolts` 54.70 V.

## How it enforces a current limit

One routine writes the field PWM register. It applies a four-tier ladder; any one of the three arms
(volts, amps, watts over target) moves it to the next tier.

| measured ÷ target amps | or volts over target by | or watts over by | field |
|---|---|---|---|
| ≤ 1.00 | | | full |
| 1.00–1.06 | 0.03 × sysMult | 1.03× | × 0.97 |
| 1.06–1.10 | 0.03 × sysMult | 1.03× | × 0.80 |
| 1.10–1.20 | 0.05 × sysMult | 1.05× | × 0.60 |
| **≥ 1.20** | **0.10 × sysMult** | **1.10×** | **0, and the stored field value is decremented by 4 (16 near the limit) every pass** |

- sysMult is 4.0 on this 48 V system, so the hard voltage arm trips at `TargetVolts` + 0.40 V.
  Lowering the voltage target abruptly zeroes the field by the same mechanism.
- The inner amps setpoint is derived as 0.98 × `TargetAmps` in the normal single-shunt case, so the
  hard cut happens at measured ≈ 1.176 × `TargetAmps` (≈ 49.4 A for a 42 A target). The 1.20
  literal is verified in the image; the 0.98 is medium-high confidence (the setpoint has several
  writers). Design against 1.10.
- The soft tiers scale only the output and recover the moment the ratio falls. The hard tier knocks
  the stored field value down every pass of the control loop, so the field collapses to zero.
- A separate ratchet cuts the field limit to 0.9 × the present field while battery amps exceed
  0.98 × `TargetAmps`. It squeezes rather than cuts.
- Out of zero there is no ramp-rate limiter: the ordinary 100 ms PID adds at most 4 raw units per
  tick (2 on 48 V systems far from target; a fast-ramp path allows up to sysMult × 25). Measured
  recovery from a zeroed field: about 2 s at zero, then about 20 A/s, roughly 6 s to settle.

**A cut in the published limit that keeps measured ÷ new limit under about 1.18 does not zero the
field.** A larger cut does. This is why the published recipes slew the BMS's current limit
([charge-limits.md](charge-limits.md)).

Zero Output Technology (protocol 201) is a different mechanism: it regulates battery current to 0 A
when the BMS asks charging to stop. It is not involved in the collapse below.

## The charge-collapse cycle with stock firmware

With stock V137.4.5, mid-bulk at 60–78 A, charge current ramps up over 8–12 s, collapses to zero in
about 300 ms and repeats. No alarm and no fault is involved (`1392`–`1394` read zero; DM_RV shows no
fault). The BMS causes it:

1. The highest cell reaches 3.400 V under charge (19 of 19 falling edges at 3399–3400 mV).
2. The BMS drops its charge current limit from 105 A to 42 A in one step (`138F` word 1 takes no
   other values).
3. The regulator, at 60–78 A against a 42 A target (ratio 1.4–1.9), hits the hard tier and zeroes
   its field. Current falls about 90 ms after the limit change.
4. With no current the IR rise vanishes and the cell falls about 30 mV.
5. The BMS's peak-hold releases at 3370–3372 mV and restores 105 A, while the regulator is still
   near zero. Go to 1.

The cycle is a transient. As the pack charges, the relaxed cell voltage rises until the 30 mV
release no longer fires, and the regulator then holds the 42 A limit (measured: 41.2 A mean, cell
3390–3393 mV, field 13 %). At the moment the top cell crosses 3.400 V the regulator's sense point
reads about 54.49 V, which is a consequence of the cell trigger, not a voltage limit in the
regulator. The BMS ladder and its constants are in [charge-limits.md](charge-limits.md).

`19FFFD80` byte 2 tracks field drive with an offset of about +47; it is not a percentage. Use the
serial `FLD%`.

## Alarm bits and faults

The `1392` reply handler turns BMS alarm bits into regulator faults. With a fault set, it zeroes its
current target and stops charging; with the low-temperature fault it also stops polling the BMS.

| Register bits | Source alarm | Regulator reaction |
|---|---|---|
| `1392` high byte (`2000` pack OV L1, `1000` pack UV L1, `0400` cell UV L1, `0200`/`0100` charge/discharge high-temp L1) | L1 | none; the handler never examines the high byte |
| `1392` `0080` / `0040` | charge / discharge low-temperature L1 | **fault 61** |
| `1392` `0020`, `0010`, `0008`, `0004` (and other bits `0020`–`0002`) | temperature-difference L1/L2, cell-difference L1/L2 | **fault 51** |
| `1392` `0001` | BMS heater output | stored, no reaction |
| `1393` `0100` | cell UV L1 | **fault 57** |
| `1393` `0400`, `1394` `0400` | pack UV L2 | fault 57 |
| `1394` `0100` | cell UV L2 | fault 57 |
| other `1393`/`1394` bits | L2 alarms | faults in the 51–61 disconnect family |

Cell overvoltage L1/L2 never reach the regulator: while a charge controller polls CAN1, the stock
BMS clears them every pass, so only cell OV L3 acts. Every L2 alarm also zeroes the BMS's own charge
current request. Which bits the published recipes mask, and why, is in
[alarms-and-contactors.md](alarms-and-contactors.md).

### Fault codes

Codes 51–61 all mean "a CAN command has been received asking" for a disconnect:

| Code | Wakespeed name | Cause |
|---|---|---|
| 51 | FC_CAN_BATTERY_DISCONNECTED | generic disconnect request |
| 52 | FC_CAN_BATTERY_HVL_DISCONNECTED | high voltage limit |
| 57 | FC_CAN_BATTERY_LVL_DISCONNECTED | low voltage limit |
| 58 | FC_CAN_BATTERY_HC_DISCONNECTED | high current |
| 59 | FC_CAN_BATTERY_HT_DISCONNECTED | high temperature |
| 61 | FC_CAN_BATTERY_LT_DISCONNECTED | low temperature |

Codes 91–93 (BMS sync lost, forced to idle, DVCC timeout) are reported over DM_RV without faulting the
regulator.

On RV-C the fault appears in DM_RV (`19FECA80`). Internal flag bits (`+0x8000` restart, `+0x4000`
soft fault) are stripped and `SPN = (code & 0xFFF) | 0x7F000` sits in the upper 19 bits of bytes 2–4
with FMI `0x1F` below it. Fault 61 is therefore `44 4C FE 07 BF FF 00 FF`; no fault is
`05 4C FF FF FF FF 00 FF`.

### Timing, measured on a running system

| Event | Time |
|---|---|
| Unmasked low-temperature L1 → fault 61 in DM_RV | 1.02 s |
| First reply carrying a bit it acts on → current from 41.5 A to under 1 A | 0.18–0.38 s |
| Alarm cleared → fault 61 self-clears, polling resumes | 15.1 s |
| Alarm cleared → fault 51 self-clears | 11.8 s |
| Pack UV L1 (`1392` `1000`) shown for 1 s | no reaction |

## Recovery with GENERAL_RESET

Some faults latch instead of clearing, and then the regulator stops polling until it is rebooted.
An RV-C GENERAL_RESET reboots it without power-cycling:

| Field | Value |
|---|---|
| DGN | `17F80` (the destination-specific form of GENERAL_RESET `17F00h`, addressed to `0x80`) |
| Priority | 6 |
| ID from source `0x82` | `0x197F8082` (`(priority << 18 \| DGN) << 8 \| source`) |
| Data | `05 00 FF FF FF FF FF FF` |

```sh
cansend can1 197F8082#0500FFFFFFFFFFFF
```

The public project rvc2mqtt implements this reset for the APS-500. After a reboot the regulator's USB
port re-enumerates, so reopen the serial port.

### After PA1 opens

The APS-500 is powered from the 48 V side of the BMS's PA1 contactor. When PA1 opens, the regulator
loses its supply (over USB alone `AST;` shows about 3.5 V and a battery temperature of −99). When PA1
closes again, it stays half-alive and does not poll the BMS until it receives a GENERAL_RESET. Any
event that opens PA1 (an L3 alarm, see [alarms-and-contactors.md](alarms-and-contactors.md)) needs a
GENERAL_RESET afterwards to restore charging.
